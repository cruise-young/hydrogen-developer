# Task Plans

> 版本: v2.3 (2026-11-13). 变更内容见文末版本记录.

## 目标与适用范围

为已确认 spec 的 Story 编写实施计划. 读者应能先看懂要解决什么问题, 为什么这样改, 改完是什么行为, 再检查执行所需的文件和契约. 技术细节支持这些判断, 不让文件清单, 方法签名或测试命令取代方案说明.

1. 开始时说明正在使用 hydrogen-task-plans. 先读取已确认的 spec, 当前代码和相关工作区约定, 核对实际复用点及改动范围.
2. 仅用于 Story. Bug 和边界明确的 Task 按普通开发流程处理, 不追加本 skill 的完整文档流程.
3. spec 未确认时先回到需求澄清. 规划中发现会改变业务行为或验收结果的缺口时, 明确指出并澄清, 不代替用户填入新规则. 沿用已有确认, 不重复询问.
4. 计划确认后通过 hydrogen-coding 逐任务实施, 不调用 executing-plans 或 subagent-driven-development. 用户负责最终评审与提交, 助手不执行 git commit.

## 沟通与通用规范

1. 文档, 日常回复, 进度汇报和交付说明遵循 hydrogen-output, 日常协作遵循下节四条规则.
2. 开始编写前读取 hydrogen-coding, 遵循其命名, 复用, 分层, 异常, 数据对象, 注释和代码风格约定. 用户明确指令优先. 不将某一项目的业务类型或基础设施写成通用要求.
3. 新增或修改内容使用英文半角标点, 包括中文说明和示例. 除标题外, 正文的阶段, 规则及验收条件用编号表示; 表格首列为序号. 标题从总结开始编号, 引用保持有效.
4. 文档写给未参与讨论的读者, 使用中文说明业务目的和改法. 专有名词, 文件名及类型名保留原名, 首次出现的必要缩写解释一次. 不使用 TS/TM/TT 等自创路径别名.
5. 文档只呈现当前有效方案. 需求澄清后原位更新规则, 任务, 示例及依赖, 删除过期方案和无关内容, 不叠加讨论历史或多轮方案对比. 实施期间进度表显示最新状态及验证结论; 完整日志优先链接已有测试报告或执行产物, 不复制进任务正文.

### 日常协作与输出规范

1. 需要行动时首行说明下一步动作; 日常问答先直接回答问题, 交付时先说明结果.
2. 多步操作使用编号, 一项说明一个动作.
3. 阶段切换时简短说明当前进度.
4. 需要确认时集中列出真正待确认的事项, 沿用已有确认, 不重复询问.

面向用户输出时遵循 `hydrogen-output`, 当前上下文未加载时先读取其 SKILL.md. 按文档, 日常回复, 进度汇报或交付说明选择输出方式; 短回复直接回答, 不展开长文档流程. 保留事实, 限制和作者意图. 用户明确要求优先; 本模块的阶段确认, 业务契约及正式文档格式继续适用. 输出优化不替代实施或验证, 不跳过审核阶段. 正式文档的章节模板不强加给日常回复和简短进度消息.

## 文档位置与信息分工

1. spec 和实施计划放在工作区根目录的同一需求目录: `设计文档/<需求名称>/`. 延续已有需求时更新其现有文件, 用户指定其他路径时以用户要求为准.
2. 新建计划通常使用 `YYYY-MM-DD-<需求名称>-plan.md`. 架构文档统一放在工作区根目录的 `架构文档/`, 不因切换子仓库或 worktree 改变归属.
3. spec 定义当前业务要求, 计划说明这些要求如何落到代码和验证中. 引用相关 spec 小节, 不在全局约束和多个任务中重复抄写公式, 字段全集或编码规范.
4. 同步维护文档互链, 源码/SQL 链接及相关索引. 对需要修正的契约先解释影响, 不能通过计划悄悄覆盖已确认的业务要求.

## 先确定整体方案, 再拆任务

按 hydrogen-coding 的 "先审视整体链路, 再确定改动落点" 核对当前代码. 在拆任务前明确从入口到处理完成的职责, 真正的同步依赖及可复用的处理链路, 说明选定落点的理由. 性能优化不能仅列出加异步或批处理, 应指出减少哪段等待或重复工作, 以及失败和一致性如何处理. 将与本需求直接相关的职责调整纳入交付, 不以修改文件最少代替整体方案合理, 也不扩大到无关重构.

同时遵循 hydrogen-coding 的 "设计阶段兼顾性能与复杂度". 整体方案简要说明实际相关的数据规模, 关键路径成本及选择依据; 简单方案足够时不添加机制. 需要新增缓存, 并发或消息链路时, 说明简单方案为何不足及维护代价, 将必要验证纳入对应任务, 不机械增加性能专题或压测任务.

## 按交付结果拆分任务

1. 任务标题表达可交付能力或可观察的行为, 例如 "结果上报后分别处理状态和结果", 避免只写 "新增DTO" 或 "修改Mapper".
2. 每个任务都应能独立审查和验证, 完成后仓库保持可编译. 相互依赖且不能独立编译的接口, 表结构和调用方变更合为一个任务; 不为了任务数量制造空接口或失效的中间状态.
3. 建模, 配置, 测试和文档步骤归入依赖它们的交付任务. 仅在确有独立价值和验证边界时另拆任务, 不按技术层机械拆分.
4. 明确真实依赖和实施顺序. 估时说明前提, 不把尚未完成的环境验证或未知范围写成确定工期. 不固定任务数, 字数, 风险数或每个任务的测试数量.

## 默认文档结构

默认使用以下四章. 复杂度需要时添加有实际内容的子节, 简单需求不为填满模板扩写. 本模板中的占位符用于说明结构, 实际交付时替换为具体内容.

```markdown
# <需求名称>实施计划

关联 spec: <可点击链接>. 更新日期: <日期>. 当前状态: <计划待确认或实施进度>.

## 1. 总结

1. 目标: <完成后增加的能力或改变的行为>.
2. 核心方案: <主要改法和选择理由>.
3. 当前状态: <已完成什么, 还缺什么, 验证范围>.
4. 下一步与待确认: <下一步动作, 真正需要决定的事项或明确为0项>.

### 1.1 任务进度

| # | 任务 | 完成后的结果 | 依赖 | 预计耗时及前提 | 当前状态 |
| --- | --- | --- | --- | --- | --- |
| 1 | <任务名> | <可验收结果> | <实际依赖> | <有依据的估算> | <待开始/进行中/代码完成但验证受限/完成> |

## 2. 整体方案

1. 当前相关链路和需要解决的问题.
2. 调整后的链路, 各方职责, 复用点及选择此处理位置的理由. 简述与选择有关的规模, 性能成本和复杂度取舍.
3. 实际影响本需求的契约变化, 风险和前置依赖. 改变异步边界时说明响应成功含义, 部分失败, 重试及一致性处理.

## 3. 实施任务

### 3.1 Task 1: <可交付结果>

1. 目标: <输入发生后, 预期产生什么可观察结果>.
2. 方案: <链路怎么调整, 复用哪些能力, 为什么这样改>.
3. 改动清单:

   | # | 所属模块 | 文件/方法 | 具体修改 | 原因 |
   | --- | --- | --- | --- | --- |
   | 1 | <模块> | <文件及方法> | <新增/修改/复用及具体行为> | <与本任务目标的关系> |

4. 实施顺序:
   1. <具体动作及完成标志>.
   2. <下一动作及依赖>.
5. 验收:

   | # | 场景 | 输入或条件 | 预期结果 | 验证方式 |
   | --- | --- | --- | --- | --- |
   | 1 | <正常场景> | <具体输入> | <可检查的输出或副作用> | <测试/接口调用/SQL或环境验证> |
   | 2 | <有意义的异常或边界> | <具体条件> | <应拒绝, 回退或保持的行为> | <对应验证> |

   技术补充: <仅在必要时列出关键签名, 执行命令, 工作目录或测试入口>.

## 4. 整体验证与交付

1. 跨任务或跨服务需要验证的完整链路.
2. 实际需要的数据库, 配置, 环境和发布顺序.
3. 交付内容及当前未完成的验证, 不将计划执行当作已经通过.
```

## 任务正文怎么写

### 1. 目标与方案

1. 目标用业务或调用方可以观察到的变化表达. 技术任务也应说明它修复的限制或带来的工程结果, 不只列类名和文件数.
2. 方案先解释从入口到结果的关键过程, 再解释代码落点. 涉及多个服务或异步步骤时, 用简短流程或必要的小图说明各方职责及先后依赖, 不让读者靠方法签名推测行为.
3. 只交代影响判断的风险和取舍. 已在 spec 确定的规则引用即可; 当前需求无关的排除项, 历史方案及已解决争论不占正文.

### 2. 改动清单

1. 每个条目说明所属模块, 文件/方法, 修改内容和原因. 新增, 修改, 复用分别写清楚, 不把调用现有能力描述为重新实现.
2. 已有本地文件使用可点击的文件名链接到绝对路径, 必要时附行号. 新文件给出明确的拟创建路径和职责; 不伪装成已经存在的文件. 名称冲突时用模块或适量路径区分, 不再要求读者查路径缩写表.
3. 只保留任务所需的文件及方法落点. 不列整棵目录树或所有 getter/setter, 也不为使清单显得完整而新增近似对象, Controller 或仓储.

### 3. 实施顺序与技术补充

1. 按真实依赖写有检查结果的动作, 例如先固定关键行为用例, 再修改事件拆分和消费职责, 最后验证重试与兼容. 保留必要的失败前验证和回归, 不把每个任务写成相同的五步测试脚本.
2. 接口路径与请求/响应, 关键字段, 表结构, 消息契约, 事务或幂等变化必须明确. 对后续任务有约束的公共方法给出准确名称, 参数及返回类型, 放在所属任务的技术补充中, 其他任务引用这一处.
3. 常规私有方法无需预先逐一规定签名, 方法体或完整测试代码. 仅在算法, 精确协议或复杂断言确实难以用文字表达时给短代码示例, 并注明用途.
4. 命令, 运行目录, 测试入口及预期成功标志放在任务末尾的技术补充中. 使用项目实际工具, 不给所有项目套用固定命令, 也不把命令退出成功当作完整业务验收.

### 4. 验收与状态

1. 用具体场景, 输入及预期结果定义验收. 不能只写 "测试通过" 或 "处理边界情况"; 覆盖正常行为及与任务有关的异常或边界, 按风险补充并发, 重试, 时间或数据一致性验证.
2. 区分计划验证与已执行结果, 单元测试与真实环境结果. 更新状态时保留最新且与当前代码匹配的验证结论, 对未验证内容及原因明确说明.
3. 风险和用例归到负责实现的任务, 全局只保留真正跨任务的验证. 不固定凑满五项风险, 不在多个章节复制同一规则或测试样例.

## 自检

完成计划后自行检查, 不默认调度子代理:

1. 只读总结和任务前两项, 能否说清完成后的效果, 核心改法及选择理由? 不清楚时先重写说明, 不继续堆方法和字段.
2. 每条当前 spec 要求是否有对应任务及可验收结果? 同时检查是否混入未授权能力, 过期方案或无关事项.
3. 改动清单能否定位文件/方法, 看出实际修改和必要性? 处理位置是否基于整体链路和真实依赖选择, 还是只在当前方法叠加? 跨任务契约, 类型名及调用关系是否一致?
4. 实施顺序是否满足真实依赖, 每个任务完成后是否可编译和独立验证? 必要的接口, 数据库和失败语义是否被过度简化?
5. 验收是否给出有意义的输入及预期结果, 技术命令是否可执行? 当前验证结论是否对应当前代码, 是否标明环境限制?
6. 是否遵循 hydrogen-coding, 中文标题和编号是否连续, 链接和章节引用是否有效, 是否使用英文半角标点?

文字或引用问题就地修正. 发现业务要求不明确时回到澄清, 不自行发明规则或在计划里覆盖 spec.

## 交接实施

1. 保存并自检后链接计划, 先请用户审阅目标, 方案, 改动范围和验收结果, 仅列真正待决定的事项. 复用已有明确确认, 不重复询问相同问题.
2. 未确认计划前不修改产品代码. 计划确认后进入 hydrogen-coding 的逐任务流程, 沿用用户明确授权及当前任务边界, 不自动提交代码.
3. 本 skill 只调整计划的表达与组织. 不因为文档变短而省略关键契约, 实际验证, 兼容要求或必要的用户确认.
