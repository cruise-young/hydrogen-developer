# Hydrogen Coding 开发规范

> 版本: v2.2 (2026-11-13). 变更内容见文末版本记录.

## 目标

依据 spec、设计方案或需求文档完成第一版开发时，优先交付清晰的整体框架、模块边界、调用链路、数据流向和改动点。控制修改范围与 diff 噪音，让 reviewer 能快速判断每项变更的目的、边界和后续工作。

不得为了让功能看起来完整而猜测业务规则、伪造外部接口结果或扩大需求范围。

## 沟通与文档格式

> 适用于 Bug、Task、Story 全流程，hydrogen-brainstorming、hydrogen-writing-plans、hydrogen-coding 三个 skill 保持同一套规则。

### 1. 日常协作与写作依赖

1. 首行说明下一步动作.
2. 多步操作使用编号, 一项说明一个动作.
3. 阶段切换时简短说明当前进度.
4. 需要确认时集中列出真正待确认的事项, 沿用已有确认, 不重复询问.

撰写或修改文档时先读取 `hydrogen-writing` 的 SKILL.md, 已在当前上下文加载时直接复用. 用它优化结构, 表达和可读性, 保留事实, 限制与作者意图. 日常短回复不机械执行完整写作流程. 用户的明确要求优先; 本模块规定的阶段确认, 文档结构, 英文半角标点及准确性要求继续适用. 写作优化不改变业务结论, 不补造缺失事实, 不跳过已规定的审核阶段.

### 2. 文档格式

适用于 spec、实施计划、改造点清单、交付说明及本流程产出的其他 Markdown 文档。

1. **先做总结**：文档标题和元信息之后，第一节为 `## 1. 总结`，3～5 条编号要点，依次写目标、关键结论或决策、当前状态、下一步、待确认事项数量。读者只看总结就能知道做什么、做到哪、下一步是什么。
2. **标题编号**：除文档标题 `#` 外，所有标题带层级序号：`## 1.`、`### 1.1`、`#### 1.1.1`；序号连续，不跳号。
3. **正文编号**：步骤、规则、要点、待确认项使用有序列表 `1.`、`2.`；表格首列为序号列 `#`；只有不可再分的并列短语可用无序列表。
4. **清晰简洁**：一条只说一件事；不写铺垫和复述；同一事实只在一处定义，其他位置用“见 3.2”引用。
5. **完整一致**：术语、类名、字段名、接口路径、错误码全文一致；改动章节后同步更新所有“见 X.Y”引用、文档互链和索引；不留 TBD 或无归属的待办。

实施计划按 hydrogen-writing-plans 的当前模板组织, 先呈现目标, 方案, 改动清单, 实施顺序和验收, 必要技术细节放在任务末尾. 文档长度以用户能判断改造及执行者能落地为准, 不为覆盖检查项而机械展开章节.

## 标点统一使用英文半角

1. 新增或修改的人工编写内容统一使用英文半角标点, 包括中文注释, 日志模板, 异常文案, 文档, 交付说明和测试中的预期文案. 中文文字保留中文, 逗号, 句号, 冒号, 分号, 括号和引号等使用 ASCII 对应字符.
2. 该约定针对本次新增或实际修改的文本, 不为标点统一批量改写无关存量内容, 不改变代码和业务语义.
3. 日志参数, 用户数据和第三方返回原文保持原值, 不在运行时统一替换其中的标点. 修改对外异常文案时同步核对协议约定及测试断言.

## 文档路径规则（所有项目）

- 所有项目的 spec 设计规格和实施文档统一存放在工作区根目录的 `设计文档/<需求名称>/`，同一需求共用一个目录，不再分别存入子仓库的 specs/plans 目录。
- 所有项目的架构文档统一存放在工作区根目录的 `架构文档/`，包括系统总览、服务边界、调用关系和整体数据流分析。
- 多仓库聚合工作区以聚合根目录为准；单仓库项目以项目根目录为准，不因进入子模块或使用 worktree 改变文档归属。
- 需求目录使用明确的业务名称，例如 `设计文档/最近执行结果查询/`；文件可保留日期和用途后缀，spec 使用 `YYYY-MM-DD-<topic>-design.md`，实施文档使用 `YYYY-MM-DD-<topic>-plan.md`。
- 延续同一需求时直接更新该目录中的现有文档. spec 只保留当前需求的最新有效内容, 澄清后直接替换旧结论, 删除已废弃或无关的内容, 不追加澄清历史, 旧新方案对照或取消事项回顾. 同步修正受影响的正文, 示例, 文档互链, 源码/SQL 链接及索引.
- 用户明确指定其他路径时优先按用户要求执行。此规则只规定文档位置，不要求为原本无需文档的任务新增 spec 或计划。

## Bug、Task、Story 分流

在进入任何重流程前，先说明本次改动的分类和理由，用户可以调整分类：

- **Bug**：恢复既有的预期行为，不新增业务能力，不主动改变对外契约。Bug 不使用 Story 的 spec、hydrogen-writing-plans 和逐任务确认流程，按普通缺陷诊断、修复和回归验证处理。
- **Task**：目标、方案和边界已经明确的有限工程或业务改动，例如配置调整、局部重构、明确的小功能。Task 不使用 Story 的完整流程，按普通开发流程处理。
- **Story**：新增或实质改变端到端业务能力，且需要系统设计及独立确认验收标准；或存在尚未明确的跨服务契约、复杂协作和兼容方案，无法按边界明确的局部任务完成。Story 必须使用本 skill 规定的完整流程。

跨模块或涉及多个文件本身不构成 Story。需求、方案、契约及验收标准明确的局部改动，即使同时修改 API、server 和调用方，仍可按 Task 执行。无法确定分类时，判断是否存在需要系统设计的业务或协作不确定性，不以模块数、文件数决定流程。实施 Bug 或 Task 时发现 Story 级范围，暂停受影响的工作，说明新增的不确定性及升级原因，再进入 Story 流程；沿用已确认的需求和结论，不重复索取同一事项的确认。不得在开发过程中把 Story 降级为 Task 以跳过确认。

## Story 完整流程

Story 按以下顺序执行，每一阶段的确认只授权进入下一阶段：

1. 使用 hydrogen-brainstorming 梳理需求、方案、正向流程、异常流程、边界条件和验收标准。
2. 生成 Story spec，完成自检并等待用户确认；确认前不得生成实施计划。
3. 使用 hydrogen-writing-plans 基于已确认 spec 生成详细计划。任务应尽量是可单独编译、测试、review 和提交的垂直切片；无法维持可编译状态的连续改动必须合并为同一任务。
4. 等待用户确认实施计划。确认前不得修改产品代码。
5. 按计划逐任务执行：先提交当前任务的改造点清单，用户确认后才开发代码、正向测试、异常或边界测试，并提供接口请求示例；完成并汇报当前任务后，更新实施计划 `1. 总结` 中的任务进度表，再进入下一任务。
6. 所有任务完成后执行整体回归，整理最终 diff、测试结果、未完成项和建议提交信息，由用户 review 并提交代码。

不得用一次确认替代后续阶段的确认。hydrogen-writing-plans 完成后固定回到 hydrogen-coding 逐任务执行，不调用 executing-plans。AI 助手不执行 `git commit`。

## 先审视整体链路, 再确定改动落点

1. 新增能力, 合并入口或优化性能前, 沿本需求相关链路查看入口校验, 编排或分发, 下游处理, 数据落库及响应时机. 核对每一步的职责, 数据来源和依赖, 不把用户指出的方法自动当作唯一改动位置. 对简单 Bug 或 Task 简短核对即可, 不额外启动完整设计流程.
2. 根据实际问题比较在当前方法扩展, 在上游统一编排, 复用独立处理链路或调整相关职责的收益与代价. 选择依据包括串行等待, 重复 I/O, 耦合, 一致性及维护成本, 不仅是修改文件少或代码离当前位置近. 先判断同步依赖是否必要, 再考虑线程, 消息, 批处理等实现手段.
3. 接口合并不代表内部处理必须合并. 多个职责能独立完成且已有可靠处理链路时, 主动评估在掌握必要上下文的接入或编排层分发, 复用既有消费者或服务. 若存在执行先后, 共享事务或必须同时成功的业务约束, 保留必要协调. 不默认在现有方法内增加异步调用, 也不把拆消息作为通用答案.
4. 改变同步或异步边界时, 明确接口成功代表已接收, 已可靠投递还是已处理, 检查实际相关的部分失败, 重试, 幂等, 乱序及事务边界. 两条消息分别发送成功不等于原子提交或消费有序; 本地异步提交也不等于可靠投递. 性能结论结合实际等待和 I/O 分析, 缺少测量时不宣称已验证收益.
5. 在已授权范围内, 主动调整直接相关的职责和调用关系, 消除新增需求暴露的不合理耦合, 不只叠加分支或包装. 向用户简短说明调整后的链路, 职责落点及理由; Story 写入现有 spec 和计划, Bug 或 Task 可直接在沟通中说明. 涉及未授权业务或外部契约变化时先说明影响, 不借整体优化进行无关重构, 不重复确认已有授权.

例如同一请求携带结果和状态, 应检查是否可在接入层分别进入现有的结果处理与状态处理链路, 而非直接让结果落库方法承担状态更新调度. 是否采用取决于两者的真实依赖和可靠性要求, 不是固定要求引入消息队列或增加服务.

## 设计阶段兼顾性能与复杂度

1. 方案设计时按实际相关性核对数据量, 请求频率或并发, 单次处理规模及响应要求, 再检查关键路径的数据库和远程调用次数, 扫描范围, 串行等待及内存占用. 区分已知事实与估算; 未知量只有会改变方案选择时才进一步核实, 不编造性能指标, 不把简单任务扩成容量规划项目.
2. 优先选择满足当前需求和有依据的预期规模的简单方案. 结合代码消除明显的循环 I/O, 重复取数和无界加载, 按需要使用已有批量能力, 合理查询或分页. 不必等到性能故障才避免这些问题, 也不为低频小数据路径进行没有实际收益的微优化.
3. 引入缓存, 并发, 新消息链路, 预计算, 分库或额外抽象前, 说明现有简单方案为何不足, 预期解决什么瓶颈, 增加哪些一致性, 资源及维护成本. 优先复用已有设施, 不为假设中的高并发或未来扩展预建通用框架. 简单方案已足够时停止增加机制, 正确性和可靠性约束仍须满足.
4. 方案说明简要给出性能依据, 主要成本和选择理由, 深度与风险相称. 对决定方案的疑点安排有针对性的 SQL 执行计划, 调用次数或关键路径测量; 不要求每个任务都做压测. 估算收益与实测结果分开, 验证满足要求后不继续无依据优化.

## 先确认最短数据链路

梳理改造点时，先从目标接口的返回字段反向追踪：字段由哪里提供、现有公开接口及其响应 DTO 是否已包含、当前代码在哪里组装目标响应。写出可直接落地的数据链路和字段映射，再决定需要改哪些文件。

- 现有接口和 DTO 已满足取数需求时，直接使用；新增转发接口、中间 DTO 或跨服务改造，须有明确的协议、权限、兼容或复用理由，不能只因项目已有相似封装就绕行。
- 区分查询时补充响应与持久化：字段仅用于本次返回时，在响应对象和查询组装处完成映射，并按实际需要接入已有依赖；确需落库、按字段执行 SQL 查询或保留历史快照时，才考虑实体、表结构及迁移。
- 对每个拟改文件说明它在最短链路中的作用。若移除某项改动仍能满足需求，就不把它纳入本次范围。
- 验证时以原始需求的返回字段和实际数据来源为准；编译通过或现有测试通过，不能代替对链路和字段落点的核对。

最短数据链路以职责合理, 业务语义正确和可靠性要求成立为前提, 不等同于只改当前方法或最少文件. 写入, 状态与消息流程同时按 "先审视整体链路, 再确定改动落点" 检查从入口到处理完成的链路.

## 优先复用现有能力, 避免过度拆分

设计改动前，先检查相关接口、类、方法、DTO、Service、客户端、转换器和调用链的职责及使用位置，判断现有能力能否直接复用或小幅扩展。此原则适用于本 skill 处理的 Bug、Task 和 Story，不限于 Dubbo 或其他特定技术。

- 职责一致、契约兼容且不会引入不合理耦合时，优先在现有合适位置扩展；不能仅因新增一个查询、操作或不同功能名称，就新建一套接口、实现类或客户端引用。
- 需要区分内部业务逻辑时，可在现有对外接口下合理组织实现，不必同时拆分对外服务。反之，不为了复用把职责无关的逻辑塞进现有大类，也不强行复用语义或字段约束不同的 DTO。
- 新增类型、抽象或调用层前，明确现有方案为何不适合，以及新增后解决的具体问题。独立权限、契约兼容、生命周期、变化原因或依赖边界等可以构成依据；“职责更清晰”“便于扩展”本身不足以证明拆分必要。
- 在方案和改造点清单中明确区分 "已有能力直接复用", "新增入口或调用", "调整存量逻辑", 逐项说明修改原因. 先选择职责, 依赖和可靠性合理的整体方案, 再控制文件数量和修改范围; 不为少改文件而增加不合理耦合或重复处理.

### 所有对象优先复用或小幅扩展

- 此规则适用于所有对象和类型，包括请求、响应、DTO、VO、Entity、领域对象、查询行 Row、事件、上下文及嵌套类型，不限于跨服务或接口对象。
- 新建类型前，先搜索同一业务及相关调用链中的现有对象。能够直接复用，或补充少量字段、方法就能满足需求且保持语义与兼容性时，复用或扩展现有对象，不新建一份近似类型。
- 不因字段略有差异、使用位置不同、需要多接收几个查询字段，就默认新建类型。先评估在现有对象补字段的影响，包括原调用方、校验、序列化、ORM 映射和依赖方向；查询或返回字段的扩展不等于必须修改数据库结构。
- 只有存在具体且无法合理消除的语义冲突、兼容性问题或依赖限制时，才新建对象，并说明已检查哪个现有类型、为什么直接复用或补字段不能满足需求；“职责更清晰”“便于扩展”不能单独作为理由。
- 能使用同一对象表达数据时，不新增仅用于逐字段复制的中间对象或转换层。复用时保留原有约束，不把业务语义不同的数据强行混在一起。

### 新建对象的 Lombok 注解

- 以后新建 Java 数据对象统一添加 `lombok.Data` 的 `@Data` 和 `lombok.experimental.Accessors` 的 `@Accessors(chain = true)`；包括请求、响应、DTO、VO、Entity、查询行、事件、上下文和嵌套数据对象。
- 不因已有 getter/setter 或使用了 `@Builder` 就省略这两个注解；链式 setter 不替代所属对象的业务校验和领域行为。
- 枚举、接口、注解类型、record，以及 Controller、Service、工具类、异常类等非数据对象不机械套用。遇到不可变对象、受保护的领域状态或继承方法签名等具体冲突时，说明原因并保留必要约束，不静默省略，也不为添加注解破坏对象不变量。
- 保留这两个注解的同时，检查生成方法：密码、令牌等敏感字段使用 `@ToString.Exclude` 或安全的显式 `toString()` 排除；包含敏感数据的嵌套对象也须检查。日志不得因打印整个对象而泄露这些数据。
- 受保护的领域状态使用字段级 `@Setter(AccessLevel.NONE)` 禁止自动生成 setter，通过有业务校验的方法修改；检查现有显式 setter，避免其绕过不变量。按对象的身份、值语义及继承关系审查生成的 `equals/hashCode`，必要时显式定制，不默认让所有可变字段参与相等性和哈希计算。
- 此约定适用于后续新建对象；不据此批量修改存量类。Review 时检查注解、import 和生成方法是否与对象契约一致。

### 请求与响应复用的补充约束

- 新建 Req/Resp 前，对比字段、语义、校验约束、序列化和依赖方向。调用方已经依赖提供方 API 模块，且契约一致时，优先直接导入该模块的类型；不能仅因跨 HTTP/RPC 或服务边界而复制同名类。
- 响应字段和语义一致时直接返回共享 Resp，不新增只做逐字段复制的响应类或转换方法。确有外部字段裁剪、脱敏、版本兼容或独立发布需求时，再说明分离契约的必要性。
- 请求中部分字段由服务端补充，不足以单独证明必须拆类。共享 Req 能保持外部必传字段、校验和序列化兼容时，可由服务端补充或覆盖内部查询字段；设备、VIN、租户等可信身份必须取自已验证上下文，不能信任客户端同名值。按副作用选择是否直接修改请求对象，避免无意改变后续日志或其他调用使用的数据。
- 调整为共享类型时，同步保留参数校验、字段类型、空结果语义和身份来源约束；删除本次重复定义和转换须在用户授权范围内，并验证身份伪造被覆盖、请求校验及响应兼容。
- 不用冗长的完整包名掩盖不必要的同名类型；先判断能否合并或复用，再正常 import。两个类型确有独立语义时可使用完整包名消歧，但应能说明保留两者的原因。解释方案时区分“技术上不能复用”与“可以复用但有明确代价”。

## Mapper 通过 Repository 仓储层访问

以下约束适用于 Bug、Task、Story 中新增的数据库访问。

- Mapper 只在仓储实现类中使用：仓储接口放在 `<服务包>.repository` 包，命名为 `XxxRepository`；实现类放在 `<服务包>.repository.impl` 包，命名为 `XxxRepositoryImpl`，标注 `@Repository` 并实现对应接口。
- Service 或 Biz 只依赖 Repository 接口，不直接注入 Mapper；Controller、Dubbo 实现、MQ 消费者等入口适配层既不注入 Mapper，也不注入 Repository，仍通过 Biz 访问。
- Repository 只负责持久化细节：查询条件、分页、排序、条件更新、乐观或条件锁等；业务判断、跨聚合编排和事务边界留在 Biz 或 Service。
- 只做一行转发、本身只封装 Mapper 增删改查的 Service，直接改为 Repository，不保留“Service → Repository”的空转发层；Service 有真实业务逻辑时才保留并依赖 Repository 接口。
- 查询结果行对象（`*Row`）等数据对象放在 `model` 包，不放在 `repository` 包；`repository` 包只放仓储接口及其实现。
- 只对本次需求新增的 Mapper 访问执行本规则；存量 Service 直接使用 Mapper 的写法不主动改造，除非用户明确要求。
- 项目存在架构约束测试（如 `ArchitectureRulesTest` 限制 Mapper 只能在 service 包使用）时，同步调整为允许 `repository` 包使用 Mapper，并把 `repository` 加入入口适配层禁止依赖的包；文件无法直接修改时，列出具体改动交由用户修改。
- 测试中 mock Repository 接口；仓储实现类的查询条件可在单元测试中初始化表元数据（如 MyBatis-Plus `TableInfoHelper.initTableInfo`）后断言生成的 SQL 片段。

## BaseEntity 与逻辑删除

以下约束适用于使用 MyBatis-Plus、已有公共实体基类的项目；VDSS task 的基线为 `com.fusion.vdss.task.server.entity.BaseEntity`。其他项目先核对自己的实体基类、DDL 和 ORM 配置，不直接照搬字段或删除值。

1. VDSS task 中主键与映射兼容的 Long 主键实体继承现有抽象 `BaseEntity`，由基类统一声明 `Long id`、`createBy`、`createTime`、`updateBy`、`updateTime`、`deleteFlag`，子类不重复声明这些字段及主键注解。基类主键使用 `@TableId(type = IdType.AUTO)`：ID 未赋值时由数据库自增并回填，已赋值时保留调用方指定的 ID（包括现有雪花 ID）；不得把 `AUTO` 理解为必须删除调用方的 ID 生成逻辑。核对实际表的自增能力及生成 SQL，不仅依据注解推断数据库支持。
2. `deleteFlag` 在基类统一使用 `@TableLogic(value = "0", delval = "1")`，`0` 表示未删除、`1` 表示已删除；使用现有 `NOT_DELETED`、`DELETED` 常量。新建、修改和删除优先复用 `init`、`touch`、`markDeleted` 等现有实体方法，保持审计信息一致；VDSS task 时间使用 UTC。
3. 继承基类前核对真实主键类型、生成策略及列。字符串主键或主键语义不兼容的实体不继承这个 Long 主键基类，独立保留所需字段和映射；例如 VDSS task 的 `TermPhraseEntity` 使用 `String id`，独立声明 `id`、`cnName`、`enName`、`deleteFlag` 及 `@TableLogic`。主键兼容但表中缺少部分审计列时，按现有方式使用 `@TableName(excludeProperty = {...})` 排除映射，不生成对不存在列的访问，不为统一继承擅自修改表结构。没有逻辑删除列或语义不兼容的实体不得强行套用；修改限定在需求范围内。
4. 经核实受 `@TableLogic` 管理的 MyBatis-Plus 内置查询，由持久层过滤已删除记录；上层不再重复检查 `deleteFlag`，新查询不重复追加同一删除条件。自定义 XML、注解 SQL、联表、子查询和统计 SQL 不能假设自动生效，必须检查实际语句，并为需要过滤的表显式限定未删除条件。
5. 逻辑删除必须实际写入删除标志及必要审计字段。不能假设 `setDeleteFlag(DELETED)` 后调用 `updateById` 就会更新逻辑列；按当前框架采用已验证的删除入口或显式 `SET`。恢复、包含已删除数据的查询使用职责明确的专用入口，普通查询不绕过过滤。涉及这类改动时验证实际生成 SQL 的删除过滤、删除写入及恢复边界，不能只靠返回实体的 mock 证明 ORM 行为。

## 查询结果与非空查询

1. 先判断业务是否要求记录必须存在：必须存在时直接复用所属 Service 或 Repository 已有的 `getByIdNonNull` 等非空查询；允许不存在、需要跳过或降级时保留 `getById` 等可空查询，不把所有读取统一改为抛异常。
2. 非空查询在所属服务的合法业务边界统一处理“查无数据”，抛出现有业务异常及对应错误码；调用方不再写 `getById` 后的重复空判断，也不在非空查询后再次判空。项目尚无此能力且本次需要时，在已有合适的 Service 或 Repository 中补充，不新增仅作转发的层；遵守前述 Mapper 访问和异常模块边界。
3. 上层直接调用现成非空查询，不另建只做查询转发、判空或重复逻辑删除判断的 `vehicleTask`、`requireTask` 等私有包装方法。真实的权限、归属、业务状态校验仍需保留，不把“非空”当成全部业务校验；可空查询的降级逻辑也不得删除。
4. 必须存在的记录由所属服务的非空查询统一抛出项目既有业务异常。ID格式校验与记录非空查询各自遵循现有职责；不为了调用非空查询新增多余的捕获转换包装，保留接口已有的参数校验、错误码和响应契约。
5. 按改动风险验证有效记录可返回、查无有效记录时抛正确业务异常；允许为空的调用仍可走原查询。Biz 测试让非空查询 mock 抛所属异常，不伪造其返回已删除实体，再要求 Biz 重复过滤；逻辑删除过滤的验证放在持久层。

## 业务异常与模块边界

以下约束适用于 Bug、Task、Story 的实现及代码审查。

- 编写业务校验前，先搜索并核对已有业务异常类、错误码、构造方法、统一异常处理器和模块依赖方向。选择能够保留当前接口错误码和文案的现有异常，不先套用通用 Java 异常写法。
- 提交改造点清单、方案或实施计划时，集中列出本次使用的异常类型（具体类名），注明复用或新增；沿用的现有类型也应列出。这里只需异常类型清单，无需逐个展开异常场景、错误码、文案或抛出位置；新增业务异常仍须取得用户确认。
- 创建业务异常实例时优先使用静态工厂；本次涉及的异常类尚未提供工厂时，优先在现有异常类中补充语义明确的静态工厂（如 `of`），再由调用方统一使用。保留原有构造方法、错误码、文案、cause及异常类型语义；不为增加工厂另建异常类，也不扩展到无关异常类或批量替换无关调用。静态工厂方法的补充不等于新增异常类型，不额外触发新异常类的确认流程。
- 已明确的业务参数不合法、业务状态不允许、业务对象不存在等拒绝场景，应在有合法依赖的业务层直接抛出合适的业务异常。已有合适业务异常时，不先抛 `IllegalArgumentException`、`RuntimeException` 等通用异常，再通过 `catch` 转成业务异常。
- 共享 API 中的枚举或工具不能依赖 server 实现模块。若业务异常只存在于 server，可让共享代码返回匹配结果、`Optional` 或校验结果，由调用方直接抛所属服务的业务异常；不得为解决依赖限制引入反向依赖或多余异常中转。若共享模块已能合法复用合适的业务异常，则直接复用。
- 移动已有异常类属于模块及契约调整，不能仅为缩短调用代码默认迁移。改动前说明迁移原因、原位置与目标位置、完整包名变化和受影响范围；核对所有引用方、统一异常处理器、模块依赖及 HTTP/RPC 的异常处理或序列化行为，评估旧调用方兼容性与发布顺序。保留既有构造方法、错误码和文案语义，并验证受影响模块；本地编译不能证明新旧服务混合部署兼容。迁移处于已授权范围时直接执行，超出范围或存在未确认的破坏性契约变化时才补充确认；新增异常类仍按下一条取得确认。
- 不能仅因现有异常不在当前模块就认定没有合适的业务异常；先判断是否能在合法依赖的调用层直接使用。确实没有合适异常时，应新建业务异常类，但必须先向用户说明现有异常不适用的原因、拟新增类的职责、所在模块、错误码和使用范围，取得明确确认后再创建。不得自行新建近似异常类，也不得用通用异常代替这一确认。
- `catch` 用于有必要的异常边界适配，例如将数据库约束或第三方调用失败转换为明确业务语义；不要为自己刚编写的业务校验添加“抛通用异常再捕获转换”的流程。真实的编程错误或未知系统故障仍按技术异常处理，不伪装成业务拒绝。
- 涉及 HTTP/RPC 时，核对业务异常在跨层或跨服务后的错误码、中文文案和统一处理行为，避免业务错误被包装成通用系统错误。需要在接口边界校验时复用同一套规则，不重复维护枚举匹配或错误文案。
- 验证应检查实际抛出的业务异常类型、错误码和文案，并按场景确认非法请求在查表、写库或外部调用前被拒绝；不能仅断言“抛出了任意异常”。

共享枚举与 task 业务层的用法示例：

```java
// 枚举可合法依赖项目已有业务异常时，查找与非法编码异常统一封装在枚举内部。
LanguageEnum language = LanguageEnum.getByCode(query.getLanguage());
```

## 请求与响应类命名

- 新增的请求参数类统一使用 `Req` 后缀，响应结果类统一使用 `Resp` 后缀；适用于 HTTP、RPC 及跨服务查询契约。
- 按对象语义命名，不再以 `DTO`、`Payload`、`Data` 或 `Rsp` 作为新增请求、响应类的后缀；响应中的嵌套结果类型同样使用 `Resp`。
- 该约定只约束请求和响应对象，不要求将 Entity、查询行、事件或领域对象改成 `Req` / `Resp`。复用存量类时保留其名称，不为统一后缀批量重命名已有类。
- 规格、计划、方法签名、类文件名及测试中的引用须保持一致。

## Controller 请求方法与路径

- 新增接口只使用 `@GetMapping` 和 `@PostMapping`，不使用 `@PutMapping`、`@DeleteMapping`、`@PatchMapping`。
- 查询类接口：带 id 的详情用 GET；分页、条件查询用 POST，路径为 `/search`。
- 写操作一律用 POST，路径用 `/动作` 或 `/动作/{id}` 表明意图，不使用只有 `/{id}` 或 `/{id}/动作` 的路径。例如：
  - 新增 `POST /create`
  - 详情 `GET /detail/{id}`
  - 编辑 `POST /update/{id}`
  - 删除 `POST /delete/{id}`
  - 启停 `POST /enabled/{id}`
  - 其他动作 `POST /resend/{id}`
- 接口权限登记（如 `am_resource` 的 `http_method`、`path_pattern`）、接口文档、`.http` 测试脚本须与 Controller 的方法和路径保持一致，修改时同步更新。
- 只约束新增接口；存量接口不为统一风格批量改路径，确需调整时先确认前端和调用方影响。

## 第 0 步：梳理并确认当前 Story 任务的改造点

开始 Story 计划中的每个任务前，任何代码新增、修改、删除、格式化或自动修复之前，必须先完成只读分析，只针对当前任务向用户提交改造点清单并等待明确确认。用户确认前不得开始写代码，也不得以“先改一部分”为由提前实施。

第 0 步允许执行的操作仅限于读取 spec、搜索代码、查看配置与数据库脚本、分析调用链、检查工作树状态及运行不改变文件的诊断命令。

改造点清单先用简短总结说明当前任务的交付结果, 改动范围, 主要风险和真正需要决定的事项. 正文按目标, 方案, 改动清单, 实施顺序及验收组织. 以下是相关性核对清单, 不是必须逐项展开的目录; 已在确认计划中写清的契约可直接引用, 只展开本轮实际变化, 不重复大段规则或命令:

1. 需求目标、非目标、当前理解，以及最短数据链路和字段映射。
2. 现有实现、主要调用链和需要保持的行为。
3. 预计新增、修改的文件，以及每个文件的方法级改动。
4. 接口、DTO、领域模型、数据库、配置、消息和外部依赖的变化。
5. 计划保留但可能废弃的存量代码，不提出直接删除。
6. 兼容性、幂等、事务、并发、数据迁移和回滚风险。
7. 尚未确认的问题、采用的假设和需要用户决定的事项。
8. 分步实施顺序，以及每一步的验证方式。
9. 本任务需要覆盖的正向流程、异常或边界流程，以及对应测试位置。
10. 涉及接口时，列出请求方式、请求地址、鉴权或请求头、示例参数和预期成功/异常响应；不涉及接口时明确标记为“不适用”。
11. 异常类型清单：集中列出本次使用的具体异常类名，注明复用或新增；新增业务异常须列为待用户确认事项。

提交清单后必须明确请求用户确认。用户调整任何改造点时，更新清单并再次确认；只有得到明确同意后，才能进入后续实现步骤。确认仅覆盖清单中的范围，实施中发现范围外改动时必须暂停并重新确认。

## 第一版实现原则

第一版优先完成：

1. 建立必要的目录、接口、类、DTO、领域对象、数据库实体、转换器和服务调用关系。
2. 串联核心流程，明确各阶段的输入、输出、异常和依赖关系。
3. 实现输入输出明确、边界稳定且不依赖未知协议的基础逻辑。
4. 对暂不具备实现条件的部分保留方法签名、返回类型、异常边界和调用关系。
5. 通过适当的编译或静态检查；无法验证的部分明确说明原因。

禁止在第一版中顺手进行无关重构、批量重命名、目录迁移、旧代码清理或统一格式化。

## 实现与占位边界

以下情况可以直接实现：

- spec 已明确输入、输出、异常和业务规则。
- 逻辑是纯函数、局部计算、数据转换或确定性校验。
- 字段含义、数据结构和兼容要求已经确定。
- 实现不会改变需求范围外的数据表、接口和业务流程。

以下情况应保留 TODO 占位：

- 外部中台、第三方服务、消息协议或存储协议尚未确认。
- 数据库字段、索引、事务边界或并发策略尚未确认。
- 需求未明确异常、兼容、状态流转或幂等规则。
- 实现会影响其他模块，但调用方和兼容策略尚未确认。

占位不能返回伪造的成功结果。根据上下文采用明确异常、安全空实现或不可用状态，并在注释中说明当前行为。

## TODO 注释规范

所有第一版占位统一使用实际日期：

```java
// todo HY YYYYMMDD
// 输入：说明参数来源、关键字段和必要前置条件。
// 输出：说明返回对象、关键字段和数据格式。
// 处理：说明后续核心步骤、校验规则和外部依赖。
// 约束：说明不参与计算、不落库、不得修改或需要兼容的内容。
```

要求：

- `HY` 固定为开发者标识。
- 日期使用编写当天的 `YYYYMMDD`，例如 `20260917`。
- TODO 紧邻待实现的方法、代码块或字段。
- 必须说明具体要实现什么，不能只写“待实现”或“后续补充”。
- 输入输出简单时可合并描述，但仍需保留职责、处理目标和关键约束。

示例：

```java
// todo HY 20260917
// 输入：DDP 文件元数据列表。
// 输出：规范化文件列表对应的 SHA-256 字符串。
// 处理：按稳定字段排序并序列化后计算 Hash。
// 约束：临时 URL 和诊断配置不参与 Hash。
```

## 注释要求

### Java 作者、日期与块注释格式

以下规则适用于 Bug、Task、Story 的 Java 开发，不以是否执行 Story 流程为前提。

- 新建 Java 类、接口、枚举、record、注解类型及测试类时，在类型声明前的 Javadoc 中填写 `@author HY` 和 `@date YYYY-MM-DD`。日期必须替换为实际创建当天的年月日，不保留占位符；修改已有文件时不改写原创建日期。
- 直接创建或写入文件时也必须主动补充作者和日期，不能依赖 IDEA 的新建文件模板。
- 所有新增或修改的 Java 块注释统一使用多行 `/** ... */` 格式；即使只有一句说明，也不得压成单行 `/** 说明 */` 或 `/* 说明 */`。
- 块注释的 `/**`、每行说明和 `*/` 分别独占一行，说明行以对齐的 ` * ` 开头。
- 块注释前与上一段代码之间必须空一行。尤其是字段注释：相邻字段之间先空一行，再写下一个字段的块注释；首个字段的块注释与类体左花括号之间也空一行。注释位于文件开头、前面没有内容时，不额外插入文件首空行。
- 块注释结束后紧接对应的注解或声明，不在注释与被说明的字段、方法或类型之间插入空行。字段说明放在字段前，不写成字段行末注释。
- Javadoc 中需要分段时，只用换行分段：段落之间保留一行只有 ` *` 的空行，不使用 `<p>`、`</p>` 等 HTML 段落标签。修改存量注释时不顺带删除原有 `<p>`，除非用户要求统一。
- 作者和日期放在类型 Javadoc 中，不重复添加到每个字段或方法的注释中。调整注释格式时限定在当前任务涉及的代码，不自动批量格式化无关存量文件。

类型注释示例（日期仅演示格式，实际填写创建当天日期）：

```java
package com.example;

import lombok.Data;
import lombok.experimental.Accessors;

/**
 * 语言包查询条件。
 *
 * @author HY
 * @date 2026-10-15
 */
@Data
@Accessors(chain = true)
public class LanguagePackageReq {

    /**
     * 目标语言编码。
     */
    private String language;

    /**
     * 当前设备绑定的车辆。
     */
    @NotBlank
    private String vin;
}
```

### 业务注释内容

注释以职责、关键业务规则、异常、副作用和必要设计原因是否解释清楚为验收依据，不设最低行数或比例。复杂模块可将约三分之一作为检查说明是否充分的参考，不作为达标门槛；简单 DTO、枚举和短方法不为比例重复代码含义。作者、日期和块注释格式仍遵循前述约定。

所有人工编写的业务注释统一使用中文，包括类注释、方法注释、行内注释、TODO、流程说明、异常说明和兼容性说明。协议名称、类型名、字段名、标准缩写及无法准确翻译的技术术语可以保留英文，但解释文字必须使用中文。

注释优先覆盖：

- 类、接口、枚举、重要字段和领域对象的职责。
- 公共方法和跨模块方法的输入、输出、异常与副作用。
- 核心流程的阶段、调用顺序、状态变化和失败处理。
- 字段映射、排序、Hash、序列化和反序列化规则。
- 数据库读写、事务、幂等、并发锁和唯一键约束。
- 临时数据、缓存数据、外部数据和持久化数据的边界。
- 新建、复用、更新、失效和删除的触发条件。
- 第一版占位与最终实现之间的差异。
- 容易误解、存在兼容要求或不能随意修改的业务规则。

以下内容不计入有效注释：

- 仅重复类名、方法名、变量名或代码行为的注释。
- 只写“调用方法”“返回结果”等没有设计信息的注释。
- 自动生成的注释、许可证头和注释掉的旧代码。
- 与当前代码不一致或未及时更新的注释。
- 为满足比例而逐行添加的无意义注释。

### 方法体内的行内注释

方法头的块注释只说明方法整体的职责、输入输出和副作用，不能代替方法体内的说明。新增或修改的方法，其方法体内必须在关键位置写中文行内注释（`//`），让 reviewer 不读被调用方法也能看懂每一步为什么这样做：

- 每个业务判断分支、提前返回或拦截条件前写一行，说明它拦截的是哪类业务情况以及原因，而不只是复述条件表达式。
- 每个流程阶段（加载、校验、查询、计算、持久化、外部调用、结果组装）前写一行，说明该阶段的业务目的。
- 查询条件、排序、比较顺序、默认值、回退分支等不直观的规则，在对应代码处写明规则和原因。
- 返回值表达业务结论时（例如“计数为 0 即为首测”），在返回语句前说明结论含义。
- 测试方法同样需要行内注释：在准备数据前说明场景和构造目的，在关键断言前说明验证的是哪条业务规则；只有一两行且方法名已能说明场景的用例，写一行场景说明即可。
- 行内注释以“一个判断或一个步骤一行”为粒度，不逐行复述代码；简单的 getter、setter、单行委托方法不强制添加。
- 交付前逐个检查本次新增或修改的方法：只有方法头注释、方法体内没有任何说明的，视为注释不完整。

示例：

```java
boolean shouldPush(DiagnosisResultEvent event, DiagnosisResultEntity result) {
    // 补报不是执行实例的基线报告，不触发推送
    if (!Boolean.TRUE.equals(event.getFullData())) {
        return false;
    }
    // 前置条件都满足后才查库：之前已有全量报告时，本次属于复测，不推送
    return ruleRepository.isFirstFullReport(result);
}
```

## 日志语言

所有人工编写的业务日志统一使用中文，日志内容应直接说明业务动作、关键对象、执行结果和失败原因，禁止只打印英文短语或含义不明的变量值。

- 日志模板遵循英文半角标点约定, 例如 `log.info("查询脚本请求, 参数={}, 请求头={}", request, headers);`. 中文说明文字同样使用英文半角标点, 日志参数保留原值.
- 参数使用占位符输出，不通过字符串拼接构造日志。
- 明细较多的上报与批处理日志以任务/报告等关键标识、状态、数量和结果为主；避免在循环内输出完整配置或反复序列化大 payload。确需保留详细内容时沿用已有日志级别与排查机制，不擅自新增日志存储链路。
- 日志中的字段名、请求 ID、任务 ID、状态码等技术标识可以保留原名，说明文字必须使用中文。
- 异常日志说明“执行什么操作时因为什么失败”，并保留必要上下文；不得记录密码、令牌、完整证件号等敏感信息。
- 不为了满足中文要求翻译异常类名、协议名或第三方返回字段。

示例：

```java
log.info("开始同步文件, 任务ID={}, 文件数量={}", taskId, files.size());
log.warn("文件校验未通过, 任务ID={}, 文件名={}, 原因={}", taskId, fileName, reason);
log.error("调用存储服务失败, 任务ID={}, 错误码={}", taskId, errorCode, exception);
```

## 充血模型

在职责边界清晰的情况下，优先采用充血模型。实体、值对象和领域对象应承载与自身数据强相关的业务行为，避免将核心规则全部堆积到无状态 Service 中。

以下封装规则适用于 Bug、Task、Story：

- 编写判断、校验、转换或派生逻辑前，先确定规则归属。只依赖某个对象自身数据、枚举编码或状态的行为，尽量封装到对应对象或枚举；即使目前只有一个调用点，也不以“只用一次”为由散落在 Controller、Biz 或 Service 中。
- 枚举集中维护编码、名称、语义判断、合法性校验与展示规则，具体遵循下节「枚举判断、校验与展示」；调用方直接表达业务步骤，不重复维护枚举规则。
- 封装遵循模块依赖方向；数据库查询、RPC 和事务编排仍留在相应服务中，不为追求充血模型把基础设施依赖塞进枚举。审查时同时检查规则归属、调用链长度和异常语义，而不只检查主方法是否变短。

适合放入领域对象：

- 对象自身可以独立完成的业务校验。
- 不变量和字段组合约束。
- 有业务语义的状态变更。
- 与对象数据紧密相关的派生计算和判断。
- 对象内部状态流转的合法性控制。

仍应放在应用服务或领域服务：

- 跨聚合业务编排和事务控制。
- 权限、身份和上下文校验。
- 外部接口、消息、缓存、文件和数据库等基础设施调用。
- 需要协调多个领域对象的复杂规则。

通过有业务语义的方法改变对象状态，不鼓励调用方连续调用 setter 拼装状态。DTO、数据库 Entity 和领域对象职责不同，不强制所有数据对象都采用充血模型。业务规则尚未确认时，先保留领域方法及 TODO 注释，不在 Service 中猜测实现。

### 枚举判断、校验与展示

1. 判断单个枚举值时，在枚举中提供静态语义方法，如 `isEmail(value)`、`isFailedOnly(value)`、`isComplete(value)`；字符串比较使用 `StrUtil.equals`。调用方不再写 `Enum.of(value) == SOME_VALUE` 或重复比较 `name()`；方法内部直接比较目标编码，不为一次判断遍历解析全部枚举。枚举实例之间的比较仍使用适合其类型的写法，不机械改成字符串方法。
2. 区分判断与严格校验：`isXxx` 对不匹配值返回 `false`；必须拒绝非法输入的规则由枚举的查找或 `validateXxx` 方法负责。在模块依赖允许时直接抛已有业务异常，调用方不通过捕获 `valueOf` 的 `IllegalArgumentException`、`NullPointerException` 判断业务输入，也不重复转换相同错误。场景与任务类型等组合约束同样由所属枚举统一校验。
3. 编码与中文名称维护在枚举字段中，通过 `getNameByValue(value)` 获取名称；调用方不再保留同义的 `switch`、多个 `if` 或只转发一次的名称辅助方法。由状态和其他结论共同决定的展示规则，提供语义明确的方法，如 `getResultName(value, validation)`，保留既有状态优先级；不把复杂展示规则硬塞进单纯的编码查找方法。
4. 明确空值、未知编码、大小写和空白的处理，沿用当前契约。展示方法可按已确认规则保留未知原值，由展示层处理空值占位；严格校验则拒绝未知值。不使用“是工厂则工厂，否则售后”这类分支，把未知编码误归为合法类型。保留历史值解析能力与限制新增、保存、启用的规则分别维护，不为收紧新写入而破坏已有 `of` 等解析方法的契约。
5. 仅收拢本次涉及的实际调用，不为未使用的枚举值批量生成方法，不统一原本语义不同的展示名称。验证已知映射、空值、未知值及严格匹配边界；涉及 JSON、Excel、邮件等输出时，按风险验证实际输出，避免只测试辅助方法而漏掉调用链。

## Redisson 回调锁工具

### 通用工具与锁键

1. 优先复用项目已有的 `RedissonLockUtil`；需要新增时只封装获取锁、执行回调和释放锁。业务 Key 及查重、状态校验、保存等业务逻辑由调用方提供，工具不承载业务事务、不内置推送规则等业务前缀，也不依赖具体业务错误码。获取超时或等待中断使用已有通用锁异常，如 `CannotAcquireLockException`；回调的业务异常原样传播。
2. 明确 `withLock(key, action)` 使用完整 Key；确需按租户路由隔离时，由 `withTenantLock(businessKey, action)` 统一追加当前可信路由，不在各入口手工拼接。多 Redis 数据源项目先通过 `RedissonClientProvider.decideRedissonClient()` 或项目等价能力选择当前路由客户端，再获取锁。结合客户端和数据源的实际隔离方式核对作用域，不能仅凭方法或变量名认定已实现租户隔离；路由缺失时的处理沿用项目明确约定。
3. 锁名反映真实资源、作用域和用途。完整键使用 `KEY`，需要追加标识的前缀使用 `PREFIX`；一把锁保护多种写操作时使用写入等准确语义，不保留仅指新增保存的名称。工具不得自行扩大为所有业务共用的全局锁。
4. 多个写入口会共同影响同一唯一性或状态约束时，使用同一作用域的锁。例如租户内规则名称唯一时，新增、编辑、启停、删除共用该租户该业务的一把写锁；已能完整保护约束时不再嵌套规则 ID 锁。独立业务或不相交的数据范围不据此强制共用锁。

### 加锁位置与事务边界

1. 入口仅来自 Controller 且无其他写入入口时，优先由 Controller 调用锁工具，回调中调用 Spring 代理的 Biz 方法；Biz 保留声明式 `@Transactional(rollbackFor = Exception.class)`。若实际存在其他入口，则按真实调用链确定共同保护位置，不以假设存在 Dubbo 或内部调用为理由强行下沉锁。
2. 需要保护的是“读取并校验 → 写入 → 事务提交或回滚”的完整范围。确认回调返回或抛出异常前事务已结束，再释放锁；核对代理调用、自调用及外层事务，避免 Biz 加入外层事务后方法虽返回、事务却尚未提交。不能只依据 `@Transactional` 注解的位置判断锁与事务顺序正确。
3. 不为调整解锁顺序引入 `TransactionTemplate` 或 `REQUIRES_NEW`；优先通过清晰的调用层级保证顺序。已有独立业务语义确需新事务时另行核对，不据此删除无关事务逻辑。依赖数据库状态的查重与状态校验须在锁保护范围内完成。

### 获取、释放与验证

1. 使用有界等待，等待时长沿用项目配置或已确认值，不将某个业务的等待秒数推广为固定规范。需要看门狗续期时使用不指定固定租期的 `tryLock(waitTime, unit)`，不同时写死短租约，导致业务尚未完成锁已过期。
2. 仅在成功获取锁且当前线程仍持有锁时，在 `finally` 中解锁；回调正常返回及抛出异常均须释放。捕获 `InterruptedException` 后恢复线程中断标记，再抛通用锁异常；未获取锁时不得执行回调或调用解锁。
3. 按实际风险验证获取失败、等待中断、回调失败、正常返回及事务提交或回滚时的持锁顺序；涉及租户隔离和跨入口互斥时核对实际 Key 与 Redis 路由。测试与实现不一致时定位原因，不通过削弱断言或删除用例掩盖问题。

## Java 变量必须显式声明类型

1. 新增或修改的 Java 代码禁止使用 `var` 和 `final var`, 变量声明必须写明具体类型. 此规则覆盖普通局部变量, 循环变量, try-with-resources 资源变量及使用 `var` 形式声明的 lambda 参数.
2. 根据表达式和使用语义选择准确的声明类型, 保留必要的泛型参数, 不用 `Object` 或原始集合类型绕过显式类型约定.
3. 测试代码和 Java 示例同样遵守此规则. 仅处理当前任务新增或实际修改的声明, 不为统一风格批量改写无关存量代码.

## Java 判空与集合创建

- Java 代码中的对象 null 判断统一使用 `java.util.Objects.nonNull(value)` 和 `Objects.isNull(value)`，不使用 `value != null` 或 `value == null`；流过滤可使用 `Objects::nonNull` / `Objects::isNull`。
- null 判断与空串、空白、空集合判断区分：仅判断字符串引用是否为 null 时也使用 `Objects`；字符串内容判断继续遵循下节 `StrUtil` 规范，集合是否为空使用对应的集合 API。
- 集合可能为 null 时，优先使用项目已有的 `CollUtil.isEmpty/isNotEmpty`；已明确非 null 的集合可直接使用 `isEmpty()`。遍历非空集合时核对分支方向，不能在 `isEmpty` 分支直接调用可能为空的集合的 `stream()`；需要将 null 视为空集合时复用局部 `safe` 方法，保留原有空值语义。
- 创建 Map、List、Set 等集合时，优先使用 Guava 的 `Maps.newHashMap()`、`Maps.newConcurrentMap()`、`Lists.newArrayList()`、`Sets.newHashSet()` 等工厂方法，按实际需要选择集合类型，保持并发性、顺序性、可变性等原有语义。
- 使用 `java.util.Objects` 及 `com.google.common.collect` 下对应工具类的普通 import。确认目标模块可合法使用 Guava，必要时按项目现有依赖管理声明直接依赖。
- 上述规范适用于本次新增或修改的 Java 代码，不为统一风格扩大到无关存量代码。

## 字符串判断优先使用 Hutool StrUtil

- 新增或修改的 Java 字符串判断优先使用 `cn.hutool.core.util.StrUtil`，包括相等、空串、空白、前后缀和包含判断；仅判断引用是否为 null 时遵循上节 `Objects` 规范；已有等价能力时，不再混用 `StringUtils`、`Objects.equals`、直接调用字符串 `equals` 或手写判空组合。
- 精确字符串比较使用 `StrUtil.equals`；空白判断使用 `StrUtil.isBlank` / `isNotBlank`，仅判断空串使用 `StrUtil.isEmpty` / `isNotEmpty`。根据业务语义选择，不能把空串与纯空白混同。
- 保持大小写、空白、null 及非法输入的既定语义。未获授权不使用忽略大小写、trim 或默认回退来兼容输入；字符串工具负责比较，业务合法性由所属模型的方法负责。
- 仅调整当前任务涉及的判断，不全仓替换；确认目标模块可合法使用 Hutool，必要时按现有依赖管理声明直接依赖。规则仅针对字符串，枚举实例等非字符串比较仍使用适合其类型的方式。

## 对象转换与方法参数

1. 字段映射、协议值到存储值的规范化放在已有 Convert/Converter 中；例如报告状态的已知值规范化、未知原文和 null 保留由 `toReport` 完成。枚举编码的解析和匹配继续复用所属枚举；业务拒绝、跨对象校验及持久化编排由业务层承担。
2. MapStruct 同名映射可以直接复用；补充服务端主键、关联信息和审计字段时，使用现有转换重载或 default 方法。避免先在 Biz 做字段转换，再让转换器重复复制或覆盖；优先扩展已有转换器，不新建仅作逐字段转发的对象。
3. 同一请求对象已经包含转换所需字段时，方法直接接收现有 payload/Req/Event，在方法内部提取字段；避免调用方拆成一长串同源标量参数。不同来源使用语义明确的重载，共用可信身份、租户等组装步骤时提取私有方法，不用冗长参数列表掩盖重复逻辑。
4. 方法名说明职责与实际粒度：保存多条功能项使用 `saveFunctionItems`，实体构造使用 `toXxx` 或项目已有命名。按独立职责提取私有方法，保持输入、输出和副作用清楚，不为缩短主流程增加无必要的类型或调用层。
5. 审计字段沿用「BaseEntity 与逻辑删除」约定；同一业务动作需要统一时间时复用已确定的时间值。仅在当前任务涉及的方法中应用这些约定，不批量整理无关代码；异步位置、消息拆分和具体状态字典仍以业务协议为准。

## 集合处理与批量持久化

1. 多条同类明细先组装实体集合，再复用现有 Repository/Service 的批量入口；循环内保留必要的转换、校验和主键关联，避免逐条数据库写入。按实际数据量和驱动能力选择有限批次，空集合跳过持久化；不为统一批量风格强改必须逐条处理的业务语义。
2. 保留主从关联、写入顺序及既定事务边界。一个报告和多类明细属于同一事务时，任一批失败向外传播，不能吞异常后返回成功；批量调用不等于已验证真实数据库回滚或吞吐收益。
3. 循环中反复按稳定键查配置时，先建立 Map 索引；保留原有首条/末条优先、重复键、空键和顺序语义，避免借优化自行改变匹配规则。集合创建沿用 Guava 约定，已满足语义的不可变集合保留其不可变性。

## 外层方法保持简洁

Controller、Biz 和应用服务中的外层方法应以业务流程编排为主，让主流程可以直接读出执行顺序。与单一聚合或单一持久化对象紧密相关的实现细节，应下沉到对应 Service、Repository 或领域方法中。

主业务方法必须保留清晰的流程编排和中文阶段注释。这里的主业务方法包括 Controller 入口、Biz 入口、应用服务入口以及承载核心用例的编排方法，并非只指 Java 的 `main` 方法。

- 按真实执行顺序组织校验、查询、领域行为、持久化、外部调用和结果组装。
- 在每个关键阶段前添加简洁的中文注释，说明该阶段的业务目的，例如“校验请求参数”“加载并校验聚合”“执行领域状态变更”“持久化并发布事件”“组装返回结果”。
- 主方法应让 reviewer 不进入被调用方法也能理解主流程、事务边界和主要失败点。
- 阶段注释必须与实际代码一致，不使用“第一步”“处理数据”等缺少业务语义的占位描述。
- 不得为了缩短主方法把完整流程隐藏到 `process`、`handle`、`execute` 等职责不明确的通用方法中。

优先下沉以下逻辑：

- `insert/update` 等持久化分支判断，封装为语义明确的 `saveOrUpdate`、`create` 或 `update` 方法。
- 仅用于转换当前聚合数据库约束的异常处理，例如把唯一键异常转换为该聚合的重复创建业务异常。
- 单个对象的校验、状态变化、字段组合和结果判断。
- 在多个外层调用点重复出现、但职责归属于同一 Service 的防御性代码。

外层方法应保留以下内容：

- 跨聚合、跨服务和外部接口的调用顺序。
- 事务边界以及影响整体提交、回滚语义的业务步骤。
- 需要组合多个结果才能作出的业务决策。
- 会改变接口语义、幂等策略或业务流程的异常处理。

避免在外层方法中保留只做一次转发的 `if/else` 或仅捕获后原样转换的 `try/catch`。下沉后仍需保证方法名能够表达副作用和异常语义，不能为了缩短外层代码而把无关职责堆进一个通用 Service 方法。

## 改动范围与 Diff 控制

- 默认只修改已授权需求涉及的文件；Story 同时遵循已确认的 spec 和改造点范围，Bug、Task 不以存在 spec 为前提。新增文件必须有单一且明确的职责。
- 不修改无关的格式、缩进、换行、import 顺序、命名和注释风格。
- 不擅自删除或替换授权范围外的存量逻辑。已授权修复、封装或重构所必需的替换及旧实现移除，按现有授权执行并验证原有契约，不重复请求确认；仅因发现无用代码而进行的额外清理仍需确认。
- 不把业务变更、架构重构和格式化混在同一个改动中。
- 发现无关工作树修改时予以保留，不覆盖、不回滚、不混入当前任务。
- 每一处 diff 都必须能对应 spec、TODO、缺陷修复或必要验证。
- 无法解释的变更应撤回或拆分，不能留给 reviewer 猜测。

## 存量代码与废弃确认

对于仅被判断为不再使用、保留后不影响当前功能且尚未获准清理的存量代码，不得顺手删除。在本次相关代码中需要记录该判断时，保持原有行为并在最接近的位置标注“可能废弃”，等待用户确认清理；不为标记废弃扩大修改范围。已授权修复或重构中必要的替换、旧实现移除按前述规则执行，不要求保留两份实现或再次确认。

统一注释格式：

```java
// 可能废弃 HY YYYYMMDD
// 当前新流程未使用，暂时保留以避免影响存量兼容；待用户确认后再删除。
```

执行要求：

- 标注前先检查引用、反射、配置绑定、序列化、数据库映射和外部调用，不能仅凭文本引用数量判断废弃。
- 注释说明判断依据、当前保留原因和可能影响，不修改原有执行逻辑。
- 注释放在最小且完整的废弃候选范围，不逐行重复标注。
- 不连带删除相关测试、配置、数据库字段、接口或兼容分支。
- 如果存量代码导致编译失败、行为冲突或安全问题，先核对证据和处理方案；属于已授权修复范围的必要删除可直接执行并验证，超出范围的清理再请求确认。
- 在交付说明中单独列出所有“可能废弃”项，方便用户集中确认。

## 分步交付

复杂需求按可独立验证的交付结果拆分任务. 以下是任务内部可采用的实现阶段, 不要求按技术层拆成五个单独任务:

1. 搭建接口、对象和调用链框架。
2. 补充数据模型、字段映射和基础校验。
3. 接入核心业务流程和状态变化。
4. 补充外部依赖、事务、幂等和并发处理。
5. 补充测试、验证和必要的异常处理。

每一步只解决一个主要问题，并保持可编译或明确说明暂时不可编译的原因。

hydrogen-writing-plans 中的一个任务是最小交付单元。当前任务完成、验证并向用户汇报后，才能提交下一任务的改造点清单。不得在一个确认中夹带后续任务，也不得为了减少轮次跨任务修改代码。

## 测试与接口示例

每个 Story 任务应根据实际改动补充测试：

- 至少覆盖被修改行为的一条正向流程。
- 至少覆盖一条有业务意义的异常或边界流程；不存在合理异常分支时说明原因，不为凑数量制造无价值测试。
- 测试失败时先说明失败原因和影响，不通过削弱断言、删除用例或扩大 mock 范围掩盖问题。
- 记录实际执行的编译、静态检查和测试命令及结果。未执行的验证必须说明原因。

涉及 HTTP 或 RPC 接口时，交付中提供可复制的测试信息：请求方式、完整或项目内可定位的请求地址、必要请求头与鉴权前提、Query/Path/Body 示例参数，以及成功和主要异常响应示例。无法启动依赖环境时，可以提供 `curl`、HTTP 文件或等价请求示例，但必须标记“仅提供调用示例，尚未完成运行验证”。非接口任务明确写“不适用”。

## Review 前检查

完成修改后：

1. 使用 `git status --short` 及开始工作时记录的状态，区分本次与原有改动，覆盖已暂存、未暂存和未跟踪文件；不得为方便审查重置、清理或重新暂存用户已有工作。
2. 使用 `git diff --stat` 和 `git diff --cached --stat` 分别检查未暂存与已暂存改动规模；使用 `git diff --check` 和 `git diff --cached --check` 分别检查空白问题，不能只运行其中一组。
3. 逐文件阅读本次相关的 `git diff` 和 `git diff --cached`；同一文件两边都有改动时同时检查两份差异和最终文件，避免合并视图隐藏暂存区中的问题。
4. 使用 `git ls-files --others --exclude-standard` 列出未跟踪文件，单独读取本次新增文件并检查内容和格式；普通 diff 不包含这些文件。核对文件数与预期一致，确认没有格式化噪音或范围外修改，不将用户已有文件算作本次产物。
5. 运行与风险相匹配的编译、静态检查和测试。
6. 核对有效注释、TODO 日期和剩余未实现项；逐个检查本次新增或修改的方法（含测试方法）在方法体内是否有关键判断和步骤的行内注释，Javadoc 分段是否只用换行、未使用 `<p>` 标签。
7. 核对实际异常类型是否与已确认改造点一致、业务校验是否复用合适的业务异常，是否优先使用静态工厂并在缺失时补充、是否有多余的通用异常捕获转换，以及跨模块依赖和对外错误响应是否正确；新增业务异常类须已获用户确认。
8. 核对字段转换是否归属Convert、同源参数是否直接复用已有对象、方法名是否匹配单条/批量职责，以及循环内是否仍有可批量的数据库写入；核对对象或枚举自身的规则是否仍散落在业务编排中，按「枚举判断、校验与展示」检查静态语义判断、名称映射、严格校验与历史解析的区别，避免重复辅助方法、先解析再比较及未知值误归类；字符串判断使用 `StrUtil`，对象判空使用 `Objects.isNull/nonNull`，集合优先使用 Guava 工厂方法并保持原有语义。
9. 核对新建数据对象的两个 Lombok 注解及生成方法，尤其是敏感字段输出、受保护状态的 setter 和 `equals/hashCode` 语义；涉及异常类迁移时，核对引用方、处理器、兼容性及发布影响。
10. 核对本次新增的数据库访问是否经由 Repository 接口：Mapper 只出现在 `repository.impl` 实现类，Service、Biz 不直接注入 Mapper，架构约束测试已同步。
11. 核对本次新增的 Controller 接口只用 GET、POST，路径为 `/动作/{id}` 形式，权限登记 SQL、接口文档和 `.http` 脚本中的方法和路径与 Controller 一致。
12. 核对本次产出或修改的文档符合「沟通与文档格式」第 2 小节：首节为编号总结，标题与正文均编号且连续，引用的章节号有效，术语全文一致。
13. 涉及实体与查询时，按「BaseEntity 与逻辑删除」「查询结果与非空查询」检查公共字段映射、主键策略、逻辑删除 SQL，以及必须存在和允许为空两类查询的选择，避免上层重复判空、重复过滤或空转发包装。
14. 涉及 Redisson 锁时，按「Redisson 回调锁工具」检查工具通用性、实际 Key 和租户作用域、跨入口互斥、通用锁异常，以及事务结束后才释放锁；不把当前源码中的注释或命名当成已验证的隔离及事务保证。

15. 涉及新增能力, 入口合并或性能优化时, 按 "先审视整体链路, 再确定改动落点" 复核职责和处理位置, 以及调整后的失败语义. 按 "设计阶段兼顾性能与复杂度" 核对规模依据, 明显的重复工作, 新增机制的必要性及验证范围, 避免遗漏瓶颈或过度设计.
16. 核对新增或修改的 Java 代码, 测试及示例使用显式变量类型, 不使用 `var` 或 `final var`, 不以 Object 或原始集合类型替代.

交付前检查本次新增或修改文本中的标点, 中文注释, 日志和异常文案也须满足英文半角要求.

## 新增类的版本控制

- 本次开发新建的 Java 类（含对应测试类）完成后，必须加入 Git 暂存区，便于随代码改动一并 review。
- 文档、设计说明、SQL 脚本等非 Java 类文件默认不加入暂存区；只有用户明确要求时才加入。
- 暂存前使用 `git status --short` 和 `git diff --cached --name-only` 核对范围，不得顺带暂存用户已有的无关文件。
- 本规则仅要求加入暂存区，不代表可以自行创建提交；是否提交仍由用户决定。

## 交付说明

每次交付按「沟通与文档格式」编写：首行写用户的下一步动作，接着用一行重述进度（例如“任务 2/6 完成：任务维度汇总已改为新口径”），再按以下编号逐项简洁说明：

1. 本次修改了什么，以及现在可以验证的具体效果。
2. 本次明确没有修改什么。
3. 哪些方法或依赖仍是 TODO。
4. 执行了哪些验证及其结果；未执行的验证及其原因。
5. 正向、异常或边界测试覆盖了什么。
6. 接口请求地址、示例参数和响应，或说明本任务不涉及接口。
7. 本任务建议纳入 review 的文件范围和建议 commit message；不得自行执行 `git commit`。

## 边界

本 skill 的 Story 流程约束第一版代码的组织、注释、领域模型和变更控制，不替代具体业务 spec，也不授权修改需求未涉及的模块、数据表、接口或外部系统。Bug 和 Task 不套用此重流程。用户的明确要求优先于本规范。
